# Security and privacy

## This repository contains demo data only

Every business, person, customer, supplier, order and figure in this project is
invented, generated by `src/lib/demo-backend/seed.ts` from a fixed seed. No
record here is derived from any real business's data.

This is a public build of a system I shipped for a working bakery. The
application code is real; the backend is not. Before publishing:

- the production database was replaced with an in-memory store,
- the seeded dataset was written from scratch, not exported,
- all `.env` files, the Supabase project reference, its anon and service-role
  keys and the session signing key were excluded,
- the production data dump, the one-off maintenance SQL scripts and the setup
  guide were excluded,
- the PWA icons were regenerated: the originals were photographs of the
  bakery's real logo, carrying its trading name, town and the owner's family
  name,
- the town used as the pickup location throughout the UI was replaced with a
  neutral term,
- the native Android receipt-printer companion app was excluded entirely.

A unit test (`src/lib/demo-backend/query.test.ts`) dumps the whole seeded
database and asserts that no real-world identifier appears anywhere in it.

## There are no secrets in this project

By design, it needs none. `.env.example` is committed and contains only
documented defaults, all optional and all empty.

**Two demo affordances that are not production practice**, both documented at
their definition:

- `src/lib/demo-backend/auth.ts` — the dashboard accepts a shared demo password
  against the seeded profiles. This replaces Supabase Auth and is not a login
  system.
- `src/lib/kiosk/session.ts` — the passcode-session HMAC key falls back to a
  published development value so the project runs from a fresh clone.
  Production requires `KIOSK_SESSION_SECRET` and refuses to start without it.

Everything downstream of identity is the real implementation: the middleware
still gates `/dashboard`, staff passcodes are still checked with bcrypt, and
sessions are still HMAC-signed, httpOnly and scoped per app.

## Security properties kept from production

- Security headers in `next.config.ts`: a Content-Security-Policy whose only
  external origin is the OpenStreetMap tile server, plus `X-Frame-Options:
  DENY`, `nosniff`, a strict referrer policy and a restrictive
  `Permissions-Policy`. `'unsafe-eval'` is added in development only, for
  React's error overlay, and never in a production build.
- Append-only audit logging on every significant action.
- Day locks: once a day is counted, financial writes dated to it are refused.
- Attendance checks — device token hash, geofence, network allowlist — all run
  server-side; the phone is never trusted.
- The takings encryption is genuine WebCrypto and runs entirely in the browser.

## Reporting

If you find a security problem — or, more importantly, if you believe anything
here identifies a real person or business — please open an issue, or contact me
directly if you would rather not do so publicly. Privacy reports will be acted
on immediately.
